## 要旨

日本の子ども食堂は、居場所と食の支援を地域で支える実践である一方、公的資金や企業支援を受けようとすると、不正受給への懸念と、使途の説明責任が同時に壁になる。他方、デジタル庁は生成AI利用環境「源内」を府省庁に展開し、成功事例の横展開を阻む四つの壁——事例を知らない、効果が不明瞭、導入方法がわからない、コストが高い——を、共通ルール、ドキュメント、オープンソース化によって下げる方針を公表している。ただし2026年8月時点で源内の主たる展開対象は政府職員であり、全国の自治体が恒常的に利用できる制度が確立したとは言えない。熊本地震の被災自治体等への緊急提供は、その例外的な位置づけとして公表されている。

本ワーキングペーパーは、著者が継続してきた子ども食堂DAOおよびMetaマルシェ構想を、上記の行政デジタル政策の文脈に接続する。提案の中核は、(a) 氏名・住所を持たない識別子による運営者・出店者の一意化、(b) 入金・支出・領収書番号をハッシュチェーンで残す監査台帳、(c) マルシェ売上の一部還元、(d) 生成AIは下書きに限り職員が確認する、の四つである。実装は Python 3.10 以降の標準ライブラリのみで再実行できる参考プロトタイプとして公開する。

## 1. 問題設定

子ども食堂運営は、食材調達、会場、ボランティア、寄付、場合によっては自治体や社協を通じた支援金が重なる。ここでの失敗モードは二つに大別できる。第一に、同一主体が名義を変えて支援を重ねる、あるいは領収書を使い回すといった、投入側が最も恐れる不正である。第二に、不正がなくても「何に使ったか」が事後に再構成できず、議会・監査・報道に耐えないことである。後者は善意の運営者にも事務負担としてのしかかる。

デジタル政策の側では、生成AIの庁内利用が府省庁で先行している。源内は、機密性を含む業務で試験できる環境を、内製と OSS 公開によって広げようとしている。しかし子ども食堂現場と源内は、所管もネットワークも利用者も異なる。安易に「自治体が源内を入れれば子ども食堂が効率化する」と書くと、事実と仮説が混線する。

本論文の問いは次である。**公金・支援金の説明責任を、個人情報を最小化しつつ機械的に補助する参考実装を、源内の「四つの壁」議論に対する応用事例として提示できるか。その際、Web3 由来の本人確認を必須化せずに設計できるか。**

- 2026年4月に OSS として公開された。
- デジタル庁内では、政府統一基準のもと機密性2情報を含むプロンプト入力、GSS 経由の SSO に対応すると説明されている。
- 横展開を阻む四つの壁（事例、効果、導入方法、コスト）を、共通ルール・ドキュメント・OSS で下げる方針が示されている。
- 国内で開発された LLM の調達・利用を通じ、日本語と文化・価値観への適合、AI 自律性を進める方針が示されている。

## 4. 提案の全体像

構想の源泉は、著者の子ども食堂DAO、資金調達、Metaマルシェに関する既発表ノート、および内閣府地方創生SDGs官民連携プラットフォーム関連の紹介である（第10節）。本版で新しく固定するのは、次の設計原則である。

**原則1. 属性を持たない一意化。** 台帳は氏名、住所、顔画像を保存しない。アクションごとの nullifier（秘密とアクションから導いたハッシュ）だけを持つ。

**原則2. 支出は再認証と領収書番号をセットにする。** 同一領収書番号の再登録は拒否する。

**原則3. マルシェは地域の稼ぐ側、食堂は還元の受け側として接続する。** デモでは売上の一定割合を還元する。料率は DAO 投票の題材にしうるが、法的な DAO 設立を主張しない。

**原則4. 生成AIは下書き。** 源内相当の要約・文案は、職員確認を前提としたスタブに留める。自動給付決定には使わない。

**原則5. 本人確認は段階的。** 既定の制度適合経路は公的個人認証・窓口確認のプレースホルダである。World ID は Sybil 耐性の比較対象とする。

この原則は、Web3 の用語（DAO、SBT、NFT）を前面に出すよりも、監査可能性と個人情報最小化を前面に出す。用語は導入障壁になりうるが、ハッシュチェーンと重複拒否は既存の内部統制議論に翻訳しやすい。

## 5. 本人確認と World ID

World ID は、World ネットワークにおける Proof of Personhood の実装の一つである。ボットによる多重登録や多重投票を抑える目的で、子ども食堂DAO構想の源流記事でも扱ってきた。しかし行政の本人確認の本線は、公的個人認証、マイナンバー利用事務、条例に基づく窓口確認である。未契約の民間生体デバイスを、子どもと公金の案件で必須化することは、調達、比例原則、報道リスクの面でコストが大きい。

よって本実装は `identity_backend` を切り替える。

- `public_credential`: 公的確認結果のハッシュだけを受け取るプレースホルダ。
- `world_id_mock`: 同一人物・同一アクションで同一 nullifier が再現されるオフライン・モック。
- 本番の World ID Cloud API は意図的に未接続とし、誤って個人情報や証明を外部送信しない。

暗号資産の受領や NFT 売上は、運営者の将来の収入チャネルとして概念的に残すが、デモの資金フローには入れない。実証の第一段階を、円建ての入金・支出・還元に限定するためである。

## 7. 参考実装の設計

モジュール `kodomo_shokudo_dao_meta_marche.py` は、次を標準ライブラリのみで行う。

- 食堂運営者・出店者の登録と、同一秘密に基づく多重登録の拒否。
- 支援金・寄付・マルシェ還元・支出の記録。
- 支出時の運営者再認証（登録時と異なるアクションの証明を要求しつつ、運営者秘密の再計算で同一性を確認）。
- 領収書番号の重複拒否。
- ハッシュチェーンの再計算による改ざん検知。
- 提案単位の一人一票。
- 三方よしレポート（支出からの概算食数、入金、残高、還元額）。概算食数は単価仮定に依存し、現地の実食数の代替ではない。

限界は明示する。初期入力が虚偽であれば、チェーンは虚偽を一貫して保存する。端末の乗っ取り、秘密の共有、紙の領収書の偽造は別問題である。DAO モジュールはガバナンスの法形式（一般社団、NPO、任意団体）を創設しない。

源内スタブは、接続されていないことを例外や文言で示す。誤接続による業務データの混入を避けるためである。

## 8. 期待効果（仮説）と検証指標

README で述べてきた波及——AI 駆動開発の訓練の場、地域の稼ぐ力、魁自治体のロールモデル、分散的な国力——は、いずれも仮説である。検証は二層に分ける。

**層A（ソフトウェアが出せるもの）**: 入金合計、支出合計、残高、チェーン整合、重複拒否の件数、概算食数。デモの `generate_sanpo_yoshi_report()` が担う。

**層B（現場が出せるもの）**: 実提供食数、利用者の継続、運営者の記帳時間、誤登録・トラブルの件数、議会説明に使えたかどうか。層Aだけで「三方よしが実現した」と書いてはならない。

費用対効果も同様である。OSS と既存の無償に近いインフラは初期検証コストを下げる方向に働くが、削減幅は未測定である。2例目以降の限界費用逓減は、一般的なソフトウェアの性質に基づく見込みに過ぎない。

## 9. リスク、倫理、コミュニケーション

子ども、貧困、公金、生体・端末証明、暗号資産は、それぞれが単独でも慎重なコミュニケーションを要する。結合すると、技術実証が「子どもからデータを取る事業」に誤読されうる。対策は、(1) 属性データを持たない、(2) 実証第一段階から暗号資産を外す、(3) 源内・World の商標を、ブランドガイドラインと利用契約なしに公式連携であるかのように使わない、(4) 効果数字を一次出典なしに繰り返さない、である。

広報の順序は、論文 DOI → コード → 2ページブリーフ → 実証打診、が妥当である。DOI を「国際的に認められた政策」と翻訳しない。プレプリントは優先権と引用可能性のための公開であり、品質保証の終了ではない。

国内での発見性を高める場合、同一本文を Jxiv 等の国内プレプリントサーバへ並行投稿することを妨げない。その場合も版と日付を揃える。
